# Working rules for this project

These are hard rules, not suggestions. Follow them on every task, no exceptions for small changes.

- **MUST read `MEMORY.md`** in the project root before starting any task — including tasks that look small, UI-only, or unrelated to backend/data. It's a running changelog of what's already been built/changed, including decisions and why (e.g. why SQL Server is used as a bridge instead of Postgres). Never redo or contradict prior work without first checking whether it's already there.
- **MUST add an entry to `MEMORY.md`** after making any meaningful change (new entry at the top, dated) — what changed, why, and anything pending or deliberately left out. This is not optional cleanup — a change is not done until it's logged. Keep entries skimmable; this file is project history, not a diff.
- If a task is finished without a `MEMORY.md` entry being added, treat that as an incomplete task and add the entry before reporting done.
- **MUST ask the user to confirm names before creating a table** — propose the table name and column names/types as a suggestion, and wait for their go-ahead (or corrected names) before running any `CREATE TABLE`. Same for adding new columns to an existing table.
- **`plan.md` (project root) is the real, authoritative end-goal plan for this project** — roles/permissions model, schema, API structure, phased roadmap, all of it. When something being built conflicts with `plan.md`, that's worth flagging, not silently overriding either side. But **do not start executing `plan.md`'s roadmap (its chunks, schema, or any of its design) unless the user explicitly asks to work on it** — for now, treat it as read/understood context only, not a queue of pending work to pick up on your own initiative.
- **When executing a `plan.md` chunk**, keep it small and independently verifiable: inspect existing code/patterns before changing anything (don't invent or duplicate systems that already exist — one auth system, one pricing engine, one booking model), never trust client-supplied role/price/status/ownership, and after the chunk run typecheck + lint + relevant tests and report which files changed and what (if anything) is still outstanding. Don't expand into a later phase's scope while the current one is incomplete.

## Publishing (deploy to the live site)

The app is hosted on **Vercel** and deploys from **`main`**. `git push origin main` **is** the publish action — treat it as such. Day-to-day work happens on **`development`** (which gets its own Vercel preview URL wired to the Neon `development` DB). Full runbook: `DEPLOY.md`.

- **Never commit or push directly to `main`.** The only thing that reaches `main` is a merge from `development`. Do not push `main` unless the user explicitly asks to publish.
- **Migrations are append-only.** Numbered `.sql` files in `db/pg-migrations/`. Never edit one that has already been applied anywhere — add a new higher-numbered file. `npm run migrate` applies them to the Neon `development` branch; production is handled automatically (next point).
- **Production migrations run automatically on deploy.** `vercel-build` runs `db/predeploy.js` (applies pending migrations to the production DB, only when `VERCEL_ENV=production`) before `next build`. A failed migration fails the build, so the previous deployment keeps serving. Do **not** also run `npm run migrate:prod` by hand as part of publishing — it would double up.
- **Before merging `development` → `main`, run `npm run db:check`** (compares the two Neon branches: migration ledger + columns + triggers + functions). It must exit 0:
  - *"IN SYNC"* or *"production is behind by N migrations, all present as local files"* → OK to publish.
  - *production AHEAD*, *applied migration with no local file*, or *schema differs while ledgers match* (a DB was hand-edited) → **stop, investigate, do not merge.** Reconcile any manual DB change into a numbered migration first.
- **Publish with `npm run publish`** (`db/publish.js`). It runs the whole sequence: refuse unless on a clean `development` → `npm run db:check` (abort if not green) → `git fetch` → fast-forward `main` to `development` → `git push origin main` (Vercel deploys) → back to `development` and push it too. Do the steps by hand only if `publish` aborts on something it can't resolve (e.g. `main` diverged). After Vercel goes green, run `npm run db:check` once more to confirm *IN SYNC*.
- **Never put secrets in `db/predeploy.js`, `db/publish.js`, `DEPLOY.md`, or any committed file.** Connection strings live in `.env.local` (local) and Vercel env vars (deployed) only.
